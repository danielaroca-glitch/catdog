## Lessons Learned

- **2026-09-10 — Nenhum controller com endpoint mapeado só pra e2e mostra cobertura no relatório do Jest — precisa de um unit test próprio, mesmo que fino, que chame o handler direto (`new Controller(mocks)`, sem `TestingModule`)** — `AnimalsController`/`SpeciesController` (pbi-001, module_002) nasceram só com e2e real (`animals-create.e2e-spec.ts`/`species-list.e2e-spec.ts`), seguindo a leitura de `testing.md` de que controllers exigem "integration" (e2e cobre isso). Rodando `npm run test:cov`, os dois apareceram em 0% de cobertura — o e2e roda numa suíte Jest SEPARADA (`test:e2e`, config própria) cujo resultado nunca é somado ao relatório de cobertura de `npm run test`. O padrão já existente no projeto (`admin.controller.spec.ts`, criado em `pbi-003`) já resolvia isso — instancia o controller direto, sem guards nem DI, testando só a delegação ao use case/serviço — mas eu não segui esse precedente por padrão, só percebi ao rodar o gate de cobertura no fechamento. Lição: todo controller precisa de DOIS níveis de teste — um e2e real (autorização/guards, correção de ponta a ponta) e um unit fino (só a delegação, pra aparecer no relatório de cobertura) — nunca assumir que "integration" no `testing.md` dispensa o segundo.

- **2026-09-10 — Radix UI `Select` (`components/ui/select.tsx`, gerado via `npx shadcn add select`) trava testes de RTL em jsdom, mesmo com os polyfills usuais de `hasPointerCapture`/`scrollIntoView`/`releasePointerCapture`** — ao construir `AnimalForm` (pbi-001, T6), abrir o dropdown (`user.click` no trigger) e clicar numa opção nunca resolvia, estourando o timeout padrão de 5s do Jest. Não investigado a fundo (pode ser uma interação específica da versão do Radix/jsdom deste projeto com `PointerEvent`), mas a correção pragmática foi trocar por um `<select>` nativo do HTML — testável direto com `userEvent.selectOptions`, sem nenhum polyfill, e visualmente estilizável com as mesmas classes Tailwind do resto do design system. Lição: para um campo de seleção simples (poucas opções, sem busca/multi-select), preferir `<select>` nativo neste projeto — só reconsiderar Radix `Select` se surgir uma necessidade real que o nativo não cubra (e, nesse caso, investigar o polyfill correto antes de gastar tempo em tentativa e erro).

- **2026-09-10 — `sonar-run` do `makuco-mcp` ainda depende do Docker Desktop, mas `complexity-check` do mesmo MCP não** — no fechamento de `pbi-001` (module_002), `sonar-run` falhou de novo com `failed to connect to the docker API` (mesmo erro documentado no fechamento de `pbi-002`/`pbi-003`), mas `complexity-check` funcionou normalmente no mesmo ambiente, na mesma sessão. Confirma que o ambiente não tem Docker Desktop rodando (não é uma falha intermitente/pontual do MCP) — mas nem toda tool do `makuco-mcp` precisa de Docker: só a que efetivamente roda um container (o scanner do Sonar). Lição: não assumir que "Docker indisponível" bloqueia TODAS as tools do MCP — testar cada uma; o fallback de `npx @sonar/scan` (já documentado) continua sendo o caminho certo especificamente para `sonar-run`/`get-sonar-issues`, não para o MCP como um todo.

- **2026-09-10 — Este ambiente não tem o Supabase CLI linkado ao projeto (sem `DATABASE_URL`/`SUPABASE_ACCESS_TOKEN`), então nenhuma migration SQL pode ser aplicada automaticamente pela sessão** — só a `SUPABASE_SERVICE_ROLE_KEY` está disponível, que autentica chamadas via `supabase-js` (leitura/escrita de linhas), mas não executa DDL arbitrário. Toda PBI futura que precisar de uma tabela/coluna nova no Supabase real vai precisar do mesmo fluxo manual: a sessão cria o arquivo `.sql` em `services/backend/supabase/migrations/` (mesmo padrão de `20260907120000_create_profiles.sql`), o usuário cola o conteúdo no SQL Editor do dashboard antes dos e2e reais dessa PBI poderem rodar. Não vale a pena reinvestigar isso a cada PBI — perguntar direto no início do desenvolvimento se a PBI tocar schema.


- **2026-09-08 — Este projeto Supabase assina JWT com chave assimétrica (ES256/JWKS), não HS256/segredo compartilhado** — ao construir `JwtAuthGuard` (T2, `pbi-003`), presumiu-se HS256 local com `SUPABASE_JWT_SECRET` como segredo compartilhado (`jsonwebtoken.verify(token, secret, {algorithms:['HS256']})`). O teste unitário passou (fabrica seu próprio token HS256 com um segredo fake), mas TODO token real do projeto era rejeitado: o JWKS do projeto (`{SUPABASE_URL}/auth/v1/.well-known/jwks.json`) só publica uma chave ES256 — `SUPABASE_JWT_SECRET` no `.env` hoje contém o `kid` da chave, não um segredo HS256 utilizável. Só foi descoberto ao escrever o primeiro e2e real que exercitava o guard (T6/T5, em paralelo — os dois acharam e corrigiram independentemente). Fix adotado: `supabase.auth.getClaims(token)` — método oficial do SDK (`@supabase/supabase-js`, já instalado), verifica localmente via WebCrypto contra o JWKS cacheado e cobre HS256 (fallback a uma checagem via rede) E ES256 (local) automaticamente, sem exigir nenhuma lib nova nem segredo compartilhado. Lição: qualquer guard/middleware de verificação de JWT contra um provedor externo (Supabase ou não) precisa ser testado contra um token REAL emitido por esse provedor antes de ser dado como pronto — um teste unitário que fabrica seu próprio token nunca vai pegar uma divergência de algoritmo de assinatura.

- **2026-09-08 — `signOut({ scope: 'local' })` NÃO é "só limpar cache local" — ainda revoga a sessão no servidor** — ao corrigir o achado #1 crítico da review do pbi-002 (cliente Supabase singleton vazando identidade entre requisições), a primeira tentativa chamou `signOut({ scope: 'local' })` logo após extrair os tokens em `LoginUseCase`/`RefreshUseCase`, presumindo que `scope: 'local'` só limparia o storage do cliente sem tocar o servidor. Errado: o GoTrue ainda chama o endpoint de logout e revoga a sessão recém-emitida (o `scope` só controla QUANTAS sessões do usuário são revogadas — `local` = só esta, `global` = todas — não SE alguma é revogada). Isso quebrou o próprio fluxo de refresh (E2E-05 real passou a falhar, pego só ao rodar a suíte e2e contra o Supabase de verdade, não pelos testes unitários mockados). Fix correto: um cliente Supabase **efêmero, um por chamada** (`createClient()` fresco, nunca reusado) para `signInWithPassword`/`refreshSession`, em vez de reusar qualquer cliente singleton — elimina o vazamento pela raiz (não há estado compartilhado) sem precisar revogar nada depois. Lição geral: qualquer "fix" que envolva chamar uma API de cleanup de um SDK de terceiros precisa ser verificado contra o comportamento REAL da API (ler o código-fonte/docs, não assumir pelo nome do parâmetro) e testado contra o serviço real antes de ser dado como resolvido — testes unitários mockados não teriam pego isso.

- **2026-09-08 — `persistSession: false` no Supabase não é "sem estado"** — a opção só troca o storage adapter (memória em vez de localStorage/AsyncStorage); o cliente ainda cacheia e usa a sessão salva para autenticar chamadas subsequentes (`_getAccessToken()` prefere `session.access_token` sobre a `supabaseKey` original). Um cliente criado com a service role key e reusado como singleton NUNCA deve chamar `signInWithPassword`/`refreshSession`/qualquer método que salve uma sessão de usuário final — isso contamina permanentemente a identidade efetiva do cliente para todas as chamadas seguintes. Lição para qualquer integração futura com Supabase Auth no backend: um cliente "admin" (service role) e um cliente de "auth de usuário final" precisam ser instâncias diferentes — na pbi-002, resolvido com uma fábrica de clientes efêmeros (`SUPABASE_AUTH_CLIENT_FACTORY`, `services/backend/src/supabase/supabase.provider.ts`).

- **2026-09-08 — Um Context Provider exportado não é o mesmo que um Context Provider conectado** — T7 criou `SessionProvider`/`useSession`, T8/T9 passaram a usá-lo, todos os testes unitários (que envolvem o componente no seu próprio provider de teste) passaram — mas nenhuma task atualizou `app/layout.tsx` para prover o contexto de verdade no app real. Só apareceu no Build-tier gate de fechamento (`next build`, prerender de `/login` explodindo com "useSession must be used within a SessionProvider"). Lição: sempre que uma task cria um Context Provider React novo, o "Done when" de ALGUMA task (a que cria o provider, ou a primeira que o consome de verdade) precisa incluir explicitamente "conectado em `layout.tsx`/app root" — testes unitários isolados nunca vão pegar isso, só o build real ou um teste de integração que rendariza a árvore inteira.

- **2026-09-07 — CORS não é pego por Supertest nem por `fetch` mockado** — O código completou 10/10 tasks com testes verdes (Supertest chama o servidor Nest direto, sem navegador; testes de frontend mockam `fetch`) mas o `code-review` (Pass 6) achou que `app.enableCors()` nunca foi chamado — um bug que só se manifesta num navegador real e que nenhum dos dois níveis de teste automatizado detecta. Lição para toda PBI futura com frontend+backend em portas/origens diferentes: `enableCors()` no bootstrap do backend é parte do "Done when" de qualquer task que exponha um endpoint consumido por fetch do browser, não algo a assumir implícito — e o code-review (não os testes) é quem efetivamente pega isso.

- **2026-09-07 — Configuração do Sonar para monorepo com testes colocados** — Context: primeira análise real do projeto (`sonar-project.properties` só tinha `projectKey`/`projectName`/`exclusions`). Problema: sem `sonar.javascript.lcov.reportPaths`, o Sonar reportava 0% de cobertura mesmo com Jest em 95%+ localmente; sem `sonar.test.inclusions`, arquivos `*.spec.ts`/`*.test.tsx` eram tratados como código de produção sem cobertura, derrubando a métrica geral; e setar `sonar.tests=.` (redundante quando os testes estão na mesma árvore que o código, sem pasta separada) zerou o escopo de `sonar.sources` inteiro, fazendo o scanner reportar "0 issues" por não analisar nada. Solução final (ver `sonar-project.properties`): `sonar.javascript.lcov.reportPaths` apontando para os dois `coverage/lcov.info`, `sonar.test.inclusions` (sem `sonar.tests`) para os padrões `*.spec.ts`/`*.e2e-spec.ts`/`*.test.ts`/`*.test.tsx`, e `sonar.coverage.exclusions` para arquivos de wiring (`*.module.ts`, `main.ts`) e primitivas geradas pelo shadcn (`components/ui/**`). O que isso evita: uma próxima PBI rodando `makuco-quality-gate` (Gate 5) não precisa reinvestigar nada disso — a config já está correta e commitada.
- **2026-09-07 — `@sonar/scan` via npx roda sem Docker/MCP** — Como `makuco-mcp` não estava conectado neste ambiente (sem `sonar-run`/`get-sonar-issues`), rodar `npx -y @sonar/scan` diretamente (com `SONAR_HOST_URL`/`SONAR_TOKEN` no ambiente) funciona como alternativa real — baixa JRE+engine na primeira vez (~10-15min), depois cacheia em `~/.sonar/cache` e cada análise subsequente leva ~1-3min. Resultados consultáveis via API REST do Sonar (`/api/issues/search`, `/api/qualitygates/project_status`, `/api/measures/component_tree`) com o mesmo `SONAR_TOKEN`.

- **2026-09-07 — Rate limiting por IP precisa de `trust proxy` explícito antes de ir para produção** — Ao corrigir o achado major de rate limiting (rodada 1) adicionando `@nestjs/throttler` com o tracker padrão (`req.ip`), a rodada 2 do review achou um problema novo: sem `app.set('trust proxy', ...)`, `req.ip` reflete o IP do proxy — não do cliente real — assim que o backend rodar atrás de qualquer reverse proxy/load balancer (praticamente todo deploy real de Node/Nest). O sintoma é pior que o problema original: todos os usuários passam a compartilhar o mesmo balde de rate limit, e qualquer combinação de 5 tentativas de QUALQUER usuário bloqueia o cadastro para TODOS por até 60s. Lição para qualquer feature futura que use `@nestjs/throttler` (ou qualquer rate limit por IP): decidir a topologia de deploy (há proxy/LB na frente?) e configurar `trust proxy` com o número exato de hops confiáveis — nunca `true` genérico — como parte do "Done when" da task, não como um follow-up.

- **2026-09-07 — Exclusão de cobertura do Jest precisa ser espelhada em `sonar.coverage.exclusions`, senão o Sonar reprova sozinho** — `configure-app.ts` já estava excluído da métrica local de cobertura (Jest `coveragePathIgnorePatterns`, ver `testing.md`), mas ninguém tinha adicionado o mesmo arquivo a `sonar.coverage.exclusions` em `sonar-project.properties`. Consequência: como o Jest nunca gera dados de cobertura para esse arquivo no `lcov.info`, o Sonar via suas 2 linhas executáveis como "a cobrir" e 0% cobertas — inofensivo enquanto outros arquivos novos diluíam a métrica de `new_coverage`, mas bastou uma PBI pequena (T13, achado #1 rodada 2) tocar só um comentário em `configure-app.ts` para o Quality Gate reprovar (`new_coverage: 75% < 80%`) sem nenhum código novo realmente descoberto. Corrigido adicionando `**/configure-app.ts` a `sonar.coverage.exclusions`. Lição: toda vez que um arquivo for excluído da cobertura do Jest por ser só testado via e2e (padrão já documentado em `testing.md`), a MESMA exclusão precisa ir para `sonar.coverage.exclusions` no mesmo commit — as duas configs são espelhadas, não independentes.

- **2026-09-08 — Reuso de refresh token no Supabase (tokens v2) não é uma janela de tempo simples — é contador + tempo, combinados com OR** — Ao escrever E2E-05 de `pbi-002` (reuso de refresh token deve invalidar a sessão), a primeira tentativa assumiu que bastava esperar o "Refresh token reuse interval" do dashboard (10s) para o reuso ser rejeitado; falhou (retornou 201, sessão válida). Causa real, achada lendo `internal/tokens/service.go` do `supabase/auth` (GoTrue): para tokens v2, `reuseAllowed := (counterDifference == 1) || (|retryStart - session.LastRefreshedAt| < reuseInterval) || allowReuseConfig`. `counterDifference == 1` (reusar o token IMEDIATAMENTE anterior ao válido atual) é tolerado **sempre**, não importa quanto tempo passe — é proteção contra perda de resposta de rede, não uma janela de retry por tempo. Só reuso de um token **2+ gerações atrás**, combinado com **nenhum refresh recente da sessão** (fora do intervalo de 10s contado do último refresh, não do token reapresentado), é rejeitado. Teste corrigido: precisa de uma rotação intermediária (para o token original ficar 2 gerações atrás) **e** esperar o intervalo depois dela, não antes do primeiro reuso. Lição para qualquer teste futuro de reuso de refresh token: um único refresh anterior nunca é suficiente para provar rejeição — são necessárias no mínimo 2 rotações antes do reuso, mais a espera do intervalo após a última rotação legítima.

- **2026-09-10 — `@Roles()` só no método é fail-open para todo handler futuro da mesma classe** — `AdminController` (T6, `pbi-003`) nasceu com `@Roles('admin')` no método `ping()`, não na classe. `RolesGuard` usa `reflector.getAllAndOverride(ROLES_KEY, [handler, class])` e trata ausência de metadata em AMBOS os níveis como "sem restrição" (retorna `true`) — um padrão deliberado para rotas que legitimamente não exigem papel. O problema: como o controller foi desenhado explicitamente como scaffolding reutilizável para futuros endpoints admin-only, qualquer handler novo adicionado sem lembrar de repetir `@Roles('admin')` nasceria acessível por QUALQUER usuário autenticado, sem aviso — o guard não distingue "rota pública de propósito" de "rota que esqueceram de proteger". Corrigido movendo `@Roles('admin')` para o nível de CLASSE (`getAllAndOverride` já dá prioridade ao método quando presente, então um handler futuro que precise ser público pode declarar `@Roles()` vazio ali). Lição: em qualquer controller cujo propósito documentado é ser base para endpoints futuros do mesmo domínio de acesso, o decorator de papel/permissão vai na classe, não no primeiro método — o padrão fail-open do `Reflector` é seguro por PADRÃO só quando o "sem restrição" é reafirmado a cada novo handler, o que não é razoável de exigir por disciplina.

- **2026-09-10 — `supabase.auth.getClaims()` faz até 2 chamadas de rede reais por token com `kid` desconhecido, mesmo sem autenticação** — lendo `GoTrueClient.js` (`fetchJwk`), confirmado que QUALQUER `kid` não reconhecido no cache local dispara um fetch ao JWKS endpoint (`.well-known/jwks.json`) toda vez — o cache só evita a chamada quando o `kid` específico já foi visto antes. Se o `kid` ainda não for encontrado após esse fetch, `getClaims` cai automaticamente para `getUser()`, uma SEGUNDA chamada de rede real. Como `JwtAuthGuard` roda antes de qualquer autenticação bem-sucedida, um atacante enviando requisições com JWTs forjados contendo `kid` aleatórios força 2 round-trips reais ao Supabase por requisição não autenticada — amplificação de DoS contra o próprio provedor de auth. Mitigado em `pbi-003` com `@Throttle` (30/min) em `/auth/me` e `/admin/ping`, mas o mecanismo em si (o SDK, não o nosso código) é o que precisa ser lembrado: qualquer endpoint atrás de `JwtAuthGuard` herda esse custo por chamada e deve ter rate limit, não só os endpoints "sensíveis" a critério do dev.

- **2026-09-10 — "sem sessão" e "sessão com papel errado" são desfechos diferentes; um guard de rota client-side não pode tratá-los como o mesmo caso** — `RequireRole` (T8, `pbi-003`) originalmente renderizava `AccessDenied` ("você não tem permissão") tanto para um visitante nunca autenticado quanto para um usuário autenticado com o papel errado. Como a sessão neste projeto é client-side-only (decisão de `pbi-002`: sem cookies/localStorage, `middleware.ts` do Next não enxerga a sessão), TODA a proteção de rota acontece num client component síncrono no render — o que faz esse componente o único lugar que sabe distinguir os dois casos. Corrigido: sem sessão → `router.push('/login')` via `useEffect` (retorna `null` enquanto isso, sem flash de conteúdo); sessão com papel errado → `AccessDenied` (mantido). Lição: ao desenhar qualquer guard de UI que substitui proteção de rota tradicional (porque a auth é client-side-only), tratar "não autenticado" e "autenticado mas sem permissão" como o mesmo estado é o erro mais fácil de cometer — são UX e ações corretivas diferentes (login vs. voltar para a própria área) e a spec/task da feature deve nomeá-los como dois cenários distintos, não um.

- **2026-09-07 — Agentes paralelos que commitam não devem compartilhar working tree** — T11 e T12 (correções de review) rodaram como sub-agentes em paralelo sem `isolation: 'worktree'`, ambos fazendo seu próprio `git add`/commit no mesmo diretório de trabalho. Como a área de stage do git é um recurso único compartilhado, os dois acabaram misturados no mesmo commit (`c775898`) por uma corrida — nenhum dano real (ambas as correções estão corretas e testadas), mas quebra a disciplina de "uma task, um commit". Lição: sempre que duas tasks paralelas do mesmo PBI vão terminar com commit próprio, usar `isolation: 'worktree'` no Agent, não rodar direto no working tree principal.

- **2026-09-10 — Um mock de módulo Jest incompleto (`jest.mock` sem todos os exports reais) mascara um erro de import que só aparece no `next build` real** — em `animals-list-view.tsx`/`edit-animal-view.tsx` (pbi-002, T6), `ApiError` foi importado por engano de `@/lib/api/animals` (que não o exporta — só reexporta implicitamente ao importar de `./auth` internamente) em vez de `@/lib/api/auth`. Os testes unitários desses dois componentes mockam `../../lib/api/animals` inteiro com um factory próprio (sem `ApiError`), então `ApiError` virava `undefined` no teste — só quebrou de forma óbvia no teste que exercitava o caminho de erro (`instanceof undefined` lança `TypeError`), e mesmo assim de um jeito que não aponta direto para "import errado". O `next build` real (que faz resolução de módulo de verdade, não mock) teria pego isso imediatamente como erro de compilação, mas só rodou no fechamento da PBI. Lição: ao escrever `jest.mock` de um módulo que reexporta algo de outro arquivo (padrão `export { X } from './y'` ou `import { X } from './y'` sem reexportar), ou o mock inclui esse export também, ou — mais robusto — o componente importa cada símbolo do módulo que realmente o declara, nunca de um módulo vizinho que só o usa internamente.

- **2026-09-10 — Uma página de edição por id sem `GET /:id` dedicado é uma decisão de escopo válida quando o recurso já tem uma listagem completa (`GET /animals`)** — `pbi-002`'s `/admin/animais/[id]/editar` busca todos os animais via `listAnimals` e filtra pelo id no cliente, em vez de um endpoint `GET /animals/:id` novo. Para uma lista pequena (dezenas/centenas de animais, sem paginação prevista ainda), isso é estritamente mais simples (zero código novo no backend) sem custo real de performance perceptível. Reconsiderar só se a listagem ganhar paginação/filtros no futuro (aí o filtro client-side por id deixa de fazer sentido, porque a página não teria mais o registro completo carregado).
